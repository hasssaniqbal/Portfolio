  • Make slow paths measurable before optimizing them.
  • Keep API contracts easy to understand.

Case studies

Performance

Making a slow API usable

A catalog API had become too slow to use comfortably. The issue was not one expensive line of code. It was repeated database work, N+1 query behavior, and joins that looked reasonable on their own but became costly together.

I reworked the read path by reducing unnecessary joins, removing N+1 patterns, introducing Redis read-through caching with practical expiry rules, and using PostgreSQL materialized views for repeated computation.

Result: response time dropped from about 50 seconds to about 3 seconds.

Search

Search indexing without wasting space

For a dataset of roughly 10 million records, search performance depended on more than adding Elasticsearch. The important work was deciding what should be indexed, how fields should be mapped, and which data did not need to be indexed at all.

The indexing and mapping strategy focused on query latency and storage footprint.

Result: index size was reduced by 50%, and query latency improved by 2x.

Async processing

Moving fragile work out of request time

Some workflows had too many stages to keep inside a single request. When one part slowed down or failed, the whole path became hard to recover.

We moved the work into RabbitMQ-backed processing with retry queues and dead-letter exchanges, so failures could be handled explicitly instead of hidden inside blocking API calls.

Result: failures became easier to handle, and long-running work no longer had to block the request path.
